# pen

Runs games compiled to WebAssembly natively and in the browser:
[gdev](../gdev), the game it grew up with, a second one in
[examples/bounce](examples/bounce), and any that `pen new` starts. The book
in [docs/](docs/SUMMARY.md) (`just docs` builds it with mdBook) begins with
your first pen game and says what a game needs. Native pen uses winit,
wasmtime, wgpu and cpal; the browser uses the same Rust runtime and renderer
with WebGPU, WebAudio and a small JSPI adapter.
The CLI compiles through Wasm plugins, reloads live games, runs tests, records
and replays sessions, and packages native players or static browser builds.

```
pen (the runtime)                           game/ (a package's bundle)
├─ winit window, input, pointer lock        ├─ game.cwasm  the Blot program, compiled ahead of time
├─ wgpu renderer     (pen-render)           ├─ game.wasm   its Wasm, for the guest ABI manifest
├─ wasmtime guest    (blot-host)            ├─ assets/     meshes, materials, WGSL, textures, sounds
├─ packets           (pen-protocol)         └─ main.scene  the starting level
├─ audio: gdev's WebAudio mix on cpal's output (WAV via symphonia, Opus via libopus)
├─ AccessKit, and services: Steam, clipboard, url, platform,
│  and deterministic noise (pen-simulation)
└─ the checkout's dev tools program (not in the player runtime)
```

The crates:

- **blot-host** runs Blot's guest ABI on wasmtime, with incremental and portable
  compilation engines.
- **pen-runtime** shares program lifecycle, the guest ABI manifest,
  transactional reload, snapshots, time travel (timeline, transport and the
  game clock), the services registry with the answers both hosts give alike,
  and the dev tools service between native and browser hosts.
- **pen-simulation** holds the simulation services both hosts answer with
  the same bits: noise and heightfields. Physics, navigation and collider
  queries belong to guest libraries or plugins.
- **pen-protocol** validates and encodes packets generated by **pen-codegen**
  from [protocol/schema.json](protocol/schema.json).
- **pen-render** draws the same packets on native wgpu and browser WebGPU.
- **pen-plugins** hosts capability-limited compiler components, which also lay
  out a checkout's tests.
- **pen** provides native windows, audio, accessibility, tooling and packaging.
- **pen-web** provides the Rust browser host and its small JSPI membrane; it is
  a workspace member that builds for wasm32 only.

## Quick start

`just install` builds the development runtime with Steam and installs it as
`~/.local/bin/pen`, a link to `~/.local/lib/pen-runtime/pen` beside Steam's
library. It also installs the smaller shipping player in `player/`; this needs
zig and cargo-zigbuild, as `just player` does. It needs binaryen's `wasm-opt` on `PATH` (a release from
https://github.com/WebAssembly/binaryen/releases; version 133 is tested) to
optimize the browser host it installs, and it removes plugins and browser host
files that earlier installs left and this one no longer builds. In a gdev
checkout (or with `--project DIR`):

| | |
|---|---|
| `pen dev` | Compile the Blot program and play, reloading the program, shaders and assets as they change, with the game's state kept, and rerunning the asset recipes whose sources change |
| `pen web` | Rust browser host with hot reload and the same Blot dev tools |
| `pen run` | Compile once and play |
| `pen build [--out DIR]` | A shippable folder: the player runtime, its Steam library and the game, precompiled (default `.pen/package`) |
| `pen build --web [--out DIR] [--zip FILE]` | The browser build as static files for any web host (default `.pen/web-export`), precompressed, with a service worker for offline play; `--zip` also packs it to upload to itch.io |
| `pen build --game DIR --out DIR` | The same shippable folder for a game bundle built elsewhere, in any language (`examples/rust-guest`) |
| `pen test [FILE]` | Golden-image tests (default `tests/visual/scenarios.json`) |
| `pen test-blot [FILE...]` | The checkout's Blot tests (default `tests/*.blot`; `--filter TEXT` runs the tests whose names hold it) |
| `pen check` | Compile the game and dev tools, and lint the assets (missing, unused, oversized, unreadable) |
| `pen assets [--check]` | Bring the assets `pipeline.json`'s steps build up to date with their sources, through the asset cache |
| `pen patch OLD NEW --out FILE`, `pen apply FILE [DIR]` | A patch between two package versions, and applying one to a package |
| `pen codegen [--check]` | Generate or check the Blot protocol |
| `pen bench` | Guest time per frame, without rendering |
| `pen packets DIR` | Each frame's input and render packet, without rendering |
| `pen gltf FILE` | Import a glTF model as assets: meshes, materials, images, skins and clips, and vertex-animation textures with `--vat FPS` ([docs/animation.md](docs/animation.md)) |
| `pen diverge REC --against DIR` | Replay an input recording on this build and another; the first frame they differ at, its packet's fields and the state's lanes ([docs/testing.md](docs/testing.md)) |
| `pen fuzz` | Random input against the game's invariants, failures cut down to a script ([docs/testing.md](docs/testing.md)) |
| `pen report FILE` | What a bug report (Ctrl+Shift+B, `.penbug`) holds; `pen --replay FILE` plays it |
| `pen texture IMAGE` | A PNG as KTX2 files for each GPU format family (BC7, ASTC, ETC2, RGBA) with every mip level; a material naming `NAME.ktx2` gets the one its device samples ([texture compression](docs/texture-compression.md)) |
| `pen font FONT` | A font's multi-channel signed distance field atlas (KTX2) and its glyphs' metrics (JSON), for text sharp at any size |
| `pen loudness FILE...` | Each sound clip's loudness (EBU R128) and true peak; `--normalize` brings them to a target ([docs/audio.md](docs/audio.md)) |
| `pen clean` | Delete pen's caches (compiled games, plugins and GPU pipelines) in the platform cache directory |
| `pen new DIR` | A new game to start from, named after DIR, which compiles and runs as it is (`--blot DIR` names the Blot checkout it builds with) |
| `pen serve`, `pen push ADDRESS` | Receive packages pushed over the network (a Steam Deck's end), and push one there ("Pushing to another machine") |
| `pen remote ADDRESS [REQUEST...]` | Ask a game run with `--devtools-listen` one dev tools request ("Remote dev tools") |

CPU captures send the normal session-start and renderer-ready events. With no
script they observe the game's authored startup; use `--script` or
`--script-file` to select the gameplay workload being measured.

Without a command, `pen` plays a packaged game: `game/` beside the
executable, or `--game DIR`. `pen --help` lists every option and environment
variable; a mistyped command or option is refused, with the nearest name.

A checkout's `pen.json` can name its game: `"game": {"name": "gdev", "title":
"gdev — Blot 3D"}`. The name is used for the data directory and the shipped
executable, and the title for the window and assistive technology. Without
it, both are the checkout directory's name. A package carries them in
`game/game.json`.

A checkout supplies `pen.json`, its compiler component settings, `src/main.blot`,
assets and a scene. Blot's native typed imports provide catalog, JSON, text,
tunables and shader declarations. No Deno is needed. Compiler temporaries live
in the platform cache directory; outputs are staged before replacing a package.

This repository's Justfile runs the same commands on `../gdev`
(`just gdev=PATH ...` for another checkout):

| | |
|---|---|
| `just dev`, `just run`, `just headless ARGS` | Play the checkout (`just dev --mute`, `just headless --frames 300 --record out.mp4`) |
| `just web` | Browser development server |
| `just itch` | `pen build --web` into `dist/web` and `dist/web.zip`, for itch.io ([docs/web-export.md](docs/web-export.md)) |
| `just test` | Everything in "Testing": `check`, `visual`, `determinism` and the full `blot-tests` suite |
| `just bench` | Guest time on wasmtime |
| `just export`, `just packets` | The bundle `dist/gdev` and the packets `dist/packets` that some tests and examples read |
| `just sync-protocol` | Regenerate pen-protocol's `packets.rs` from the checkout's schema |
| `just examples` | `examples/`' games and a new one from `pen new`: their tests, golden images and a headless run |
| `just docs` | The book in `docs/` as a site, in `docs/book` (needs mdBook 0.5) |
| `just package` | `pen build` into `dist/package` |
| `just player`, `just windows`, `just install-player`, `just ship` | The player runtimes, and packages with them ("Shipping") |
| `just slr`, `just steam-smoke APP_ID` | The Linux package in the Steam Linux Runtime containers, and against a live Steam client ("Shipping") |

Saves, preferences and crash reports live in the platform data directory
(`~/.local/share/<name>` on Linux, `<name>` being the game's name), or in `--data DIR`.

## Developing

### Hot reload

`pen dev` keeps the checkout's Blot compiler open, and it writes each new
build to `.pen/runtime/game.wasm` in one rename. It watches files through one
watcher: the plugin builds' sources, `.pen/runtime`, `src/assets` and
`pipeline.json`'s sources share it. The runtime compiles the new
build on a background thread, then moves the running state into it between
frames: the new program restores a snapshot
of the old one's state and draws a frame before it replaces it. A build that
fails to compile, start or take the state leaves the old one running, and the
console says why.

An invalid game frame pauses `pen dev` at its last accepted state instead of
closing it. The window, dev tools and watcher keep running; a valid reload
resumes playback unless you paused it yourself. Decode errors identify the
protocol field, item, lane and rejected value, with optional application
provenance ([packet diagnostics](docs/packet-diagnostics.md)). Play can retry
the running build.

In `pen dev` a guest that runs 5 s without answering the host is stopped, and
that frame is rejected the same way: the game pauses at the last frame it
finished, its program restored from the timeline, and the message's Wasm
backtrace shows where it looped. Only the development engine checks the time,
at every function entry and loop head, which costs gdev's guest 30 to 50% more
cycles per frame. Elsewhere a game that sends nothing for 60 s ends with an
error instead of hanging. Compiled games are cached in `~/.cache/pen/wasm`,
keyed by SHA-256 of the module and the engine's configuration; the eight used
last stay, and none unused for two weeks.

The state survives most edits. gdev saves it in keyed, versioned sections, one
per saved type (gdev's README, "Saved state"). A new build keeps each section
saved with its type's current version, migrates one saved with another
version through the type's `migrate`, starts afresh a type the state lacks or
cannot migrate, and drops sections no type reads any more. With gdev's explicit Ink state adapter, the runtime reports
what it did not simply keep:

```
Blot reloaded; kept 1 of 2 saved sections; migrated section 100 from version 1 to 2; dropped section 104 (no longer saved)
```

Starting from a saved state, loading a quicksave and loading the editor's
scene go through the same restore and report the same way. Only a build with
another `state_schema`, the save format's own version, is refused until a
restart.

Hot reload compiles with blot-host's development engine: Cranelift without
inlining, and an in-memory incremental cache that reuses each unchanged
function's machine code, so a small edit recompiles only what it touched.
Without inlining, gdev's first compile drops from about 360 to 105 ms and a
reload's from about 100 to 50 ms, for slower guest code ("Performance");
every other command compiles with inlining. `BLOT_INLINING=1` or `0` turns
it on or off for every command, to compare (`just compile-time` times both
engines). The game and the dev tools share the development engine and its
cache, which keeps at most 64 MB of compiled functions. From a new `game.wasm` to the new build running, the runtime's side
of a reload takes about 90 ms. The Blot compiler's build comes before that
and prints its own time (`blot: Game compiled (1.05 s)`); gdev's README puts a
build at 1 to 2 s.

Asset files reload in the renderer and audio once they have been quiet for
15 ms, and the old version draws until the new one is ready. A changed catalog
arrives with a new build, and a deleted asset keeps its last version until it
comes back. After a reload, Ctrl+Shift+R replays the last 5 s of input on the
new build ("Recording, replay and time travel").

### Wasm plugins

A plugin is a WebAssembly component implementing [wit/pen-plugin.wit](wit/pen-plugin.wit),
the versioned package `pen:plugin`: pen refuses, before linking it, a plugin
built for a version it does not host, and [wit/CHANGELOG.md](wit/CHANGELOG.md)
records each version and the shape a test holds the WIT to.
Compiler sessions build Wasm or diagnostics, report watched paths and close
explicitly; diagnostics include optional details, and file queries use portable
`/` paths. The same component lays out the checkout's tests for `pen
test-blot`: which modules there are, the entry each builds as, and what its
tests must do (return passing check reports, trap at `unreachable`, or fail to
compile with given diagnostics). pen only builds and runs them as Wasm.

A checkout selects its compiler in `pen.json`:

```json
{
  "plugins": {
    "blot": {
      "read": ["../blot2/std"],
      "run": { "blotc": "../blot2/generated/compiler/blotc.gz" },
      "timeout": 300
    }
  },
  "compiler": {
    "plugin": "blot",
    "settings": {
      "std": "../blot2/std",
      "imports": { "game/": "src/", "pen/": "pen/" },
      "nativeAssets": { "roots": ["src", "devtools"] }
    }
  }
}
```

Ordinary `pen test-blot` also accepts a library with only `pen.json`, without
`src/main.blot`, assets or a renderer. The Blot plugin's compiler settings can
supply a test layout:

```json
"tests": {
  "entry": "tests/test_fixture.blot",
  "files": ["tests/math.blot", "tests/ui.blot"]
}
```

`entry` is a shared virtual file, not a file to create: each test module's
source stands there, so `./check` resolves to `tests/check.blot`. Keeping one
entry lets workers reuse compiler sessions across modules. `files` is the
ordered default suite; explicit CLI files override it and `--filter` still
applies. Omit either field to retain its game default: an entry beside
`src/main.blot`, and discovery in `tests/`, `tests/traps/` and
`tests/rejected/`. `--session` scenarios still require a game checkout.

Plugins receive clocks, randomness and log lines (their stdout and stderr)
through WASI; files and subprocesses require the grants in `pen.json`. Each
instance's memory is capped at 1 GiB, and each call into a plugin has a
deadline (`timeout`, 300 s unless set): past it the plugin's waits on its
compiler time out, the compiler is killed, and pen opens a fresh session once
before reporting the build failed. Components are found in `PEN_PLUGINS`,
beside the executable in `plugins/`, in the local plugin build, or at an
explicit `wasm` path, and each is compiled once into `~/.cache/pen/components/`.
pen keeps its plugin caches bounded: compiled components and unpacked programs
keep the four used last and none unused for two weeks, and a plugin's own
directory loses files unchanged for two weeks and its oldest beyond 2 GiB.
`just plugins` builds them and `just plugin-tests` tests them.
Player builds omit the compiler and plugins. A checkout without a compiler
selection reports the missing configuration.

### The asset pipeline

gdev's `pipeline.json` maps the files its assets are built from (model
scripts, `.blend` files, fonts, other recipes' outputs, as globs) to the
Justfile recipes that build them. `pen dev` reruns a recipe once its sources
have been quiet for 250 ms, and what the recipe writes into `src/assets`
reloads like any asset edit. Recipes run one at a time, in the file's order,
so one that reads another's output runs after it. A change that arrives while
a recipe runs queues it again, and a file counts as changed only when its
content does, so rewriting an identical output sets nothing else off. Each
line a recipe prints comes after its name; a recipe that fails is reported,
and the game keeps the assets it has. Recipes that need a program that is not
installed (`requires`: Blender, ffmpeg) are named once at startup and
skipped. `pen dev --no-pipeline` turns the pipeline off; gdev's README
("Rebuilding assets as you edit") describes the recipes.

A recipe can import a glTF file as it is: `pen gltf models/x/x.glb` writes
its meshes (skinned ones with their rig and the file's animations as clips),
materials and images into `src/assets`, and lists them in `x.import.json`
([docs/animation.md](docs/animation.md), which also covers posing skinned
draws, vertex-animation textures and particles). gdev's `sprout` recipe
imports `models/sprout/sprout.glb` whenever it changes.

Each recipe also names the files it writes (`outputs`), which makes the
pipeline a graph: a recipe runs after those whose outputs it reads, and what
it wrote is kept in the asset cache, a content-addressed store keyed by the
recipe and its sources' contents (`PEN_ASSET_CACHE`, else
`~/.cache/pen/assets`). Sources it has built before, in this checkout or any
other sharing the cache, a CI runner's included, bring their outputs back
without running it. `pen assets` brings every recipe's outputs up to date
that way (`--check` only says which differ), built-in steps such as the
`atlas` packer run beside the recipes, and `pen check` lints what is in
`src/assets`. [docs/assets.md](docs/assets.md) has the details.

### The browser

`pen web [--port N]` serves a checkout on localhost, choosing a free port from
8000 by default. Game, dev tools and assets reload after edits. Tunables Bake
writes through the local server. `pen build --web --out DIR` exports a static
site with the Rust host, game, dev tools, scene and assets, Brotli and gzip
copies of the files that compress and a service worker that fetches those,
keeps the game for offline play and serves it cross-origin isolated
([docs/web-export.md](docs/web-export.md): hosts and itch.io); static sites
keep saves and preferences in browser storage and have no source Bake
endpoint. The dev tools' `/export` and `/import` move saves as files, and
`/record` makes a link that replays the input (`#replay=` or
`?replay=FILE.penrec`; a recording dropped onto the page plays too).

The host requires WebGPU, a secure context (HTTPS or localhost), and either WebAssembly JSPI or a
cross-origin isolated page, where it runs the game's programs in workers. `just install` includes it; `PEN_WEB_HOST=DIR` selects another build.
The server answers only to its own loopback address and port, and Bake takes
only JSON posted from its own page.
See [crates/pen-web/README.md](crates/pen-web/README.md) for building and
headless browser verification.

The browser runs time travel, the dev tools' requests and the services through
pen-runtime exactly as native pen does. Its canvas is backed by device pixels
(`devicePixelRatio`), the export's `game.json` titles the page, and saves are
written off the frame's path.

### System traces

`PEN_TRACE_SYSTEMS=/tmp/systems.json pen dev` records a native game's
`main_trace` entrypoint. Ink's `ink/pen/host.run_traced` provides this entrypoint's
observer protocol; it takes the same host capability as `main`. Rebuild Blot
and the game with the optional `blot:allocation` export before capturing.
Normal runs retain the original module and entrypoint.

Exit normally to finish the Chrome/Perfetto JSON and its adjacent
`systems.summary.json`. With this capture enabled, `/systems` also shows mean requested KiB and allocation count per call. Timing-only windows show allocation traffic as unavailable. These counts include reused arena blocks and exclude headers/size-class rounding; they are traffic, not live memory.

Spans carry stage, system name/id, frame, elapsed
microseconds, allocation requests and requested bytes. The summary has calls,
total/mean/max time, total/mean bytes, allocation count and aborted calls.
Reloaded guests share the capture and get separate timeline tracks.
`PEN_TRACE_LIMIT=N` bounds timeline events (default 1,000,000); aggregate counts
continue, and the report records how many events were omitted.

Measurements cover guest work, excluding host waiting and GPU execution.
Requested bytes include allocator reuse and are not live memory or heap
capacity. Begin-marker bridge setup is excluded from a system's measurement;
the remaining observer overhead and development engine still affect timings.
Enclosing `Guest` command spans include tracing overhead and overlap the
systems inside them. This capture is supported by the native host.

After `just export`, compare every packet and the final saved world with and
without tracing using
`PEN_TRACE_FIXTURE=dist/gdev/game.wasm cargo test -p blot-host --test system_trace -- --ignored`.

### The dev tools

The dev tools are the checkout's own: a second Blot program beside the game
(gdev's `devtools/main.blot`, its console and diagnostics, written with the
game's interface packages), which `pen dev` and `pen run` build and run
while the game runs, drawing its sprites over the game's frame. pen hosts it
and draws nothing of its own; gdev's README ("Dev tools") says what it does.
A checkout without one runs without dev tools.

It is a program of its own, with its own state, outside the game's saves,
recordings and timeline: it keeps running while the game is paused,
rewinding, failing to build or stopped on an error, and what it is told
(frame timings, the log) never reaches the game, so determinism and
recordings are untouched. Each frame (`crates/pen/src/devtools.rs`):

- **Input.** It gets every window event before the game, key repeats
  included, and the key left of 1 always as the backquote, which the game
  never sees. Its interface says what it takes from the game: the keyboard
  while one of its nodes has the focus (its console's input; the game gets
  FocusLost then, so held keys let go), and the pointer and wheel over its
  dialogs. A drag the game started stays the game's.
- **What it asks.** The `devtools` service (`protocol/schema.json`,
  DevtoolsOperation): the log (the game's reports, the Blot compiler's
  output, reloads, assets, recipes, time travel), the last frame's numbers
  (DevtoolsFrame: frame interval, the frame's phases when it asks for
  timing, draws, meshes, memory, size, the timeline's state, what culling
  left out, triangles, the render scale, and the GPU's time over each part
  of a recent frame where it has timestamps) and the GPU's name come back
  in its next frame; game console commands, pause, play,
  step, rewind, replay, keeping history, input recordings, shots, tunable
  values and bake are carried out.
- **Drawing.** Its sprites, through a renderer of its own (so its assets'
  events never reach the game), over the window's image only, never into
  screenshots, recordings or headless output; its interface hangs from the
  window's accessibility tree.

Its build (`.pen/runtime/devtools.wasm`) compiles beside the game's (lines
in the log name its entry); a new one is picked up with its state carried
over, as the game's is, as soon as the session's file watcher sees it written. Its state is kept in the checkout's
`.pen/devtools.state` between windowed sessions (the console's history, the
diagnostics' level). `--overlay` or `PEN_OVERLAY=1` opens its console from
the start. `--overlay-shot PNG` and its `/shot` save the frame with the dev
tools over it, headless too (where a run waits for its build and its
assets). A `/shot` or `/record` without a file name writes to the checkout's
`.pen/shots` or `.pen/recordings`, named for when it was made (UTC, to the
millisecond: `20261016-142301-123.png`); each directory keeps the newest 50
the dev tools named. A script's `overlay=/COMMAND[,ARG...]` step types a line into its
console (opening it first), so

```sh
pen run --headless --frames 300 --script "overlay=/diagnostics,high" --overlay-shot shot.png
```

shows the diagnostics without a window; a headless run keeps no state. They
are the `devtools` cargo feature, on by default; the player runtime leaves
them out.

Beside the console, `/timeline`, `/tunables` and `/builds` open its panels
(gdev's `devtools/panels.blot`): time travel and recordings, the live tunables
with reset and Bake, and the build and reload output. Time travel also works
from the console (`/pause`, `/play`, `/step`, `/rewind`, `/replay`,
`/history`, `/record`) and its keys ("Recording, replay and time travel").

Applications can also publish typed fields, stable object identities and
decision reasons through the opt-in [semantic inspection service](docs/semantic-inspection.md).
Both hosts support named diffs and transition watches on the existing timeline;
the application supplies its inspector UI.

The same dialog has the inspectors (gdev's `devtools/pages.blot`), whose
numbers the host works out alike for every host (`pen_runtime::inspect`):

- **Timeline:** pictures of the game's frames every 30 frames, which the host
  scales on the GPU into the dev tools' atlas (a texture of their catalog's
  `devtools_atlas` material, `crates/pen/src/devtools/pictures.rs`); a click
  goes back to one. `/watch KEY LANE is|not|below|above|changes [VALUE]`
  pauses the game once a lane of its saved state comes to compare so (the
  host looks after each frame while one is set) and the log says where.
- **Packets** (`/packets`): each of the last 120 frames' input and render
  packets, by section; pressing two frames shows how many elements of each
  section differ between them.
- **State** (`/state`): the saved state's sections, how many lanes of each
  changed since 1, 3 or 10 s back (from the history's moments), and a
  section's lanes with the changed ones starred.
- **Profile** (`/profile`): samples the game's guest about every millisecond
  of its running time (`pen dev`: the development engine's epoch ticks faster
  while it samples, its deadline counting time) and shows a flame graph and
  the functions found running most. Functions show by index until Blot
  emits a name section (`blot_host::function_name` is the one lookup).
- **Memory** (`/memory`): the guest's committed memory and the ownership
  counters guest ABI 3 exports (`blot:rc_*`, `blot:cycle_*`), with rates, and
  the host's calls (`blot_host::Probe`).
- **Assets** (`/assets`) and **Material** (`/material`): the catalog's
  meshes, materials and sounds and where each stands in the renderer, a
  preview the dev tools' renderer draws into their atlas, hot swaps (an entry
  drawn from another asset until the next build, also `/swap`), and a
  material's color and instance parameters as sliders, each change written
  into its `.material.json`, which reloads.

The Tunables page and `/preset` keep named presets of the game's values in
the checkout's `src/tunable_presets.json`, and `/bake [NAME]` writes one
value or all. The console keeps macros: `/macro NAME LINE; LINE` saves one
that `/NAME` runs, and the list after a slash offers them.

A script's `overlay-shot=NAME` step saves the frame with the dev tools over
it to the shots directory, as `--overlay-shot` does the last one.

#### Remote dev tools

`--devtools-listen ADDRESS` (`pen`, `pen dev`, `pen run`; for a packaged game
too) answers the dev tools service over TCP as the dev tools are answered, a
service state for each connection (`crates/pen/src/remote.rs`, messages of
`pen_runtime::remote`). `pen remote ADDRESS frame` prints the last frame's
numbers, `pen remote ADDRESS log --follow` tails the log, `pen remote ADDRESS
pause` pauses, and every DevtoolsOperation works so (`--text` gives a
request's text). A browser tab cannot listen; it would take a relay through
`pen web`, which is not built yet.

### Live tunables

A number to get right by feel, such as how fast the camera zooms or the gnorps
walk, can be a live-tunable constant, declared in the checkout's
`src/tunables.json` (gdev's README, "Tunables"). Setting one needs no build:
it reaches the game as a Tune input event in the next frame the game runs, so
recordings, replays and rewinds keep it. `/tune` in the dev tools' console
lists them with the values the game holds, and `/tune NAME VALUE` sets one,
as the script step `tune=NAME=VALUE` does. Baking the game's values into the
file as the defaults uses the Rust Bake service in the tunables panel; the
game then rebuilds, reloads and keeps them, so nothing moves.

### Headless runs, scripts, screenshots and videos

```sh
# The editor, then play, a shot, three strikes on the rock and another shot.
pen run --headless --shots shots --script "key=Tab wait=60 shot=playing click=470,150 click=470,152 wait=30 shot=struck quit"
# Ten seconds of 1080p60 video with the game's sound, at a steady clock.
pen run --headless --size 1920x1080 --fps 60 --frames 600 --record clip.mp4
# The same while watching it in a window.
pen run --size 1920x1080 --record clip.mp4 --frames 600
```

- `--headless` draws offscreen, as fast as the machine allows, on a steady
  clock: every frame is exactly `1/fps` of game time (60 unless `--fps`), so
  runs and recordings are repeatable whatever the frame rate. It needs
  `--frames`, a script or a replay to know when to stop.
- Before the clock starts, headless runs and recordings settle: they draw the
  first frame until every asset has loaded and faded in and the loading veil
  is gone (`--no-settle` skips it). After that a frame depends only on game
  time and input, so the same script gives the same pixels.
- `--record FILE` (`.mp4`, `.mkv`, `.webm`) is steady by construction: frame N
  of the video is game time N/fps, ffmpeg receives a constant-rate stream, and
  the game's sound is mixed offline so that exactly N x 48000/fps samples
  accompany N frames, by the same mixer the window plays ("Sound"). However
  slow a frame is to draw, the video does not stutter or drift. In a window
  the frames are also paced to the wall clock, so the game runs at its real
  speed while you play and record; `--size` pins the frame size whatever size
  the window gets.
- `--script` (or `--script-file`) takes the steps
  with `wait key down up type move glide click press release drag
  wheel shot save load`, plus `quit`, `tune=NAME=VALUE` (above),
  `console=CODE[,ARG]` (a console command by number: `console=3,12` hires
  twelve gnorps), `overlay=/COMMAND[,ARG...]` (a line typed into the dev
  tools' console, above), `overlay-shot=NAME` (a shot with the dev tools
  over it), the time travel steps ("Recording, replay and
  time travel"), `ui=NODE,ACTION[,VALUE]` ("Accessibility"), and a gamepad,
  touches, the locked mouse and an input method (`pad=`, `touch=`, `lift=`,
  `motion=`, `compose=`, `commit=`: [docs/input.md](docs/input.md)). Coordinates are page pixels of a
  page 960 wide, scaled to the viewport, so scripts land in the same places
  at 1920x1280 (the headless default).
  `move=X,Y` is instant; `glide=X,Y,FRAMES` uses smoothstep easing from the last
  scripted pointer position (initially `0,0`) without clicking, over exactly
  `FRAMES` frames. `FRAMES` must be a positive integer; the next step runs after
  arrival. At `--fps 60`,
  `glide=480,270,45` takes 0.75 s. For a smooth drag, use
  `press=left glide=X,Y,FRAMES release=left`.
- `--screenshot PNG` writes the last frame; `--frames N` stops after N.
- `--frame-budget MS` turns on dynamic resolution: the scene's render scale
  drops (to half at most) while the GPU takes longer than MS milliseconds a
  frame, and rises again when it takes well under (pen-render's
  ARCHITECTURE.md). It makes frames depend on the GPU's speed, so scripted
  shots and golden tests leave it off.

## Recording, replay and time travel

gdev is a pure function of its input: from the same state, the same frames of
input give the same render packets, bit for bit. The runtime builds on that.
gdev saves all the state later frames read, its interface's included, so a
rewind runs each frame again exactly as it first ran; a moment is 2–6 KB (a
pathfinding request in flight adds about 20 KB).
[docs/determinism.md](docs/determinism.md) has the contract, what keeps runs
inside it, what breaks it, and what it costs.

| | |
|---|---|
| `--record-input FILE` | Records the session's starting moment, then every frame's input, flags and loaded states, to a `.penrec` |
| `--replay FILE` | Plays a recording in place of the player's input and clock: the same frames, bit for bit. Headless, the run ends with it; in a window it pauses there, and Ctrl+Shift+P plays on, live |
| `--trace FILE` | A line per frame: its number, and the hashes of its input and packet |
| `--history` | Keeps the last 30 s to rewind, replay and put in a bug report (always on in a window, in `pen dev`, in replays, and in scripts that go back or write a report) |

In a window, time travel is on keys the game never sees:

| Keys | |
|---|---|
| Ctrl+Shift+P | Pause or play |
| Ctrl+Shift+period | Step one frame |
| Ctrl+Shift+comma | Step back one frame |
| Ctrl+Shift+R | Replay the last 5 s (after a reload, on the new build) |
| Ctrl+Shift+B | Write a bug report: the last 30 s of input, the state, the log and the system, in `reports/` of the data directory (`pen report FILE`, [docs/testing.md](docs/testing.md)) |

Scripts have the same as steps: `pause`, `resume`, `step[=N]`, `rewind=N`
(frames) and `replay=SECONDS`. The dev tools' console has them too, and
`/record [FILE]` starts or stops an input recording in the middle of a
session.

**Edit and replay.** In `pen dev`, pause when something goes wrong
(Ctrl+Shift+P), so the moment stays in the history while you edit. Save the
Blot fix. When the reload is in, press Ctrl+Shift+R: the last 5 s of input
play again on the new build, starting from the state before them, and then the
game plays on live.

A recording replays exactly only on the build that made it, and it does not
record which build that was (docs/determinism.md, "What breaks it").

## Net sessions and spectating

Several players on their own machines play one game, and peers send nothing
but their input: each computes the same frames from it. A game declares its
players in `pen.json` (`"game": {"players": 2}`), and its frames' input
lists every player's events behind `Player` events. Each peer predicts what
it has not heard yet and rolls back through the timeline when a prediction
proves wrong.

| | |
|---|---|
| `--net PLAYER:ADDRESS,...` | Plays as PLAYER (from 0) of a net session over UDP, every player's address in order |
| `--broadcast ADDRESS` | Streams the final frames to viewers over WebSockets |
| `--spectate ADDRESS` | Watches a stream as it comes, as a replay plays |

[docs/netplay.md](docs/netplay.md) has the contract, the wire, what a
rollback costs and what is left; `tests/net.sh` runs both through the binary.

## The boundary

### Protocol

The host and the game exchange two packets a frame. The input carries the
elapsed game time, the viewport and the events: keys, pointer, wheel, focus
lost, console commands, preferences, Tune, UiAction, assets ready or failed,
service answers, and gamepads, actions, text and an input method's
composition, the locked mouse's motion, touches and their pans and pinches
([docs/input.md](docs/input.md): what both hosts send alike, the game's
actions and their bindings, Steam Input). The render packet carries what to draw, the sound, the
interface's nodes, service requests, and requests to checkpoint, undo, redo,
save, load or exit. A game's own events and render sections, which its
`pen.json` declares, travel in both without a change to the protocol
([docs/extensions.md](docs/extensions.md)). pen-protocol's `packets.rs` is generated from `protocol/schema.json`, which also generates the game's Blot encoders and decoders. After a schema change,
`just sync-protocol` regenerates it, and `just check` fails while it is
stale.

A frame may retain ordinary mesh instances between accepted frames. Set
`retained_enabled`, send a full `retained_reset` on the first frame, then send
only `instances` updates and `instance_removals`. Identities use two exact
16-bit words. Instances sort by `(order, identity)` and are inserted at
`retained_after` in the immediate draw list; pose indices refer to immediate
draws and are adjusted by the runtime. Retained draws have no extra uniform
vectors. The combined draw count is bounded by `MAX_DRAWS`.

The shared native/browser game runtime prepares each delta transactionally and
publishes it only when the frame is validated and accepted. Rejected frames
leave the cache unchanged. Disabling retention clears it. Restore, reload and
rewind replace the guest/cache together, so the next retained frame must reset.
Downstream renderers and frame inspection receive complete ordinary draw lists.

### Services

The game reaches the platform and native libraries through one boundary,
gdev's `packages/services.blot`: it asks in its render packet's `services`
section (a request id, a service and operation code, four numbers and values,
text as code points), and each request is answered once, as ServiceAnswer and
ServiceData events in a later frame's input. Answers are input, so an input
recording holds them: a replay, a rewind or a step through recorded frames
plays them back and calls no service (`pen_runtime::services`; native pen's
own services are in `crates/pen/src/services/`). The
runtime's services:

| Service | What it does |
|---|---|
| `steam` | Achievements, stats, rich presence and the Workshop (levels players publish and subscribe to) through the Steam client; `unavailable` without one |
| `clipboard` | Copies text to the system clipboard or reads it (arboard: X11 and XWayland, Windows, macOS) |
| `url` | Opens an http or https address in the player's browser |
| `platform` | The operating system, the player's locale, and whether this is a Steam Deck |
| `noise` | Simplex noise in octaves (fBm or ridged): heightfields for terrain, or heights at points |

`PEN_SERVICES_LOG=1` prints a line for each request and what it was answered.
A native library becomes a service by implementing the `Service` trait (its
code, and an answer for each request, now or later through `poll`) and
registering it in the session's `Services`; the service and its operations get
codes in `protocol/schema.json` (`just sync-protocol`), and the game asks
through `services.blot`. `pen_simulation::Noise` is one example.

The simulation services (`crates/pen-simulation`) keep nothing between
requests: each carries its noise settings, as the schema's `NoiseOperation`
lays them out,
and the game keeps its world in its own state, so a rewind or reload asks the
same and is answered the same. Their answers are the same bits on x86_64 and
in the browser's wasm32: `pen_simulation::conformance` holds fixed requests
and the digest of their answers, which `cargo test` checks natively and
`node crates/pen-web/tests/services.mjs` (after `crates/pen-web/build.sh`)
and `just conformance` check in the browser host. The former physics, grid
pathfinding, navmesh and collider-query service IDs remain reserved and
answer `unknown`. Games implement navigation in their guest libraries.

### Other guests

The boundary is the guest ABI and the packets, not Blot: `examples/rust-guest`
is a small game in Rust that pen plays, packages (`pen build --game`) and
rewinds unchanged. A trap names its frames and, given a source map, their
files and lines ([docs/source-maps.md](docs/source-maps.md)). Mods are extra
guests beside the game, each in a sandbox with the capabilities its manifest
asks for, adding to the player's input (`--mod DIR`,
[docs/mods.md](docs/mods.md)). State is opaque by default. An explicit
[state adapter](docs/state-adapters.md) adds format-specific tooling. Ink
applications can declare saved types in `saved.json` beside the catalog for
migration fallback ([docs/saved-types.md](docs/saved-types.md)).
[docs/guest-abi-next.md](docs/guest-abi-next.md) says which of blot2's guest
ABI pen hosts and what it needs next.

### Sound

gdev declares its sound every frame, whole: buses, the voices it keeps playing
by id, and sounds played once (gdev's README, "Sound"). The browser plays it
with WebAudio (`pen-web/src/audio.rs`). Here `audio/mixer.rs` emulates the same graph
sample for sample: each node's arithmetic, `setTargetAtTime` glides, linear
fades, the k-rate playback rate, Butterworth lowpasses with Chrome's
coefficients, StereoPannerNode's mono and stereo laws, and clips resampled to
the output rate as Chrome's decodeAudioData resamples them (`resample.rs`).
`audio/reverb.rs` is the shared reverb: the same generated impulse response as
the browser's ConvolverNode, convolved in two uniformly partitioned stages
(128-sample blocks for its first 2048 samples, 2048 for the rest), which, like
the ConvolverNode, adds no latency. Live, the mixer runs in the output device's
callback (cpal; `audio/device.rs` starts the stream again when the device goes
away or the default device changes), and each frame's mix lands at the start
of its next 128-sample quantum. Ogg Opus clips decode through libopus
(opusic-sys), PCM WAV clips through symphonia. Recordings run the same mixer
offline at 48 kHz, writing it to disk frame by frame.

[docs/audio.md](docs/audio.md) covers the rest: voices and sounds placed in
the world (PannerNode's equal-power panning, matched to Chromium's), clips
streamed as they play, the output's latency and `--audio-buffer`, the dev
tools' meters, mute and solo, `pen loudness`, and captions.

Mixing a run's packets both ways (`PEN_MIX_PACKETS=DIR PEN_MIX_ASSETS=DIR
PEN_MIX_OUT=FILE cargo test --release -p pen mix_packets -- --ignored`
here, the retired TypeScript mixer in Chromium's OfflineAudioContext there) gave the
same sound to about -64 dB, and the same 100 ms envelopes to 0.01 dB.
`PEN_RECORD_PCM=FILE` also writes a recording's mix as raw f32 stereo, before
it is encoded.

### Accessibility

The game declares its interface as a tree of nodes every frame (gdev's README,
"Accessibility"): the HUD, the build bar, the station, the menus and settings,
and the level editor's toolbar. The runtime shows it to assistive technology
through [AccessKit](https://accesskit.dev) (`accessibility.rs`, with
`accesskit_winit`: AT-SPI on Linux, UI Automation on Windows, NSAccessibility
on macOS), in the player runtime too, and the dev tools' own tree (their
program's interface) is grafted under it while it shows. Each node has its role, name, description,
value, states, range and the actions it takes, and lies where the game draws
it, scaled to the window. The game drives the keyboard focus itself (F10, Tab,
the arrows, Enter: the same in the browser); the tree's focus follows it, or
the dev tools' while one of their nodes has the keyboard. An assistive
technology's action on a game node reaches the game as a `UiAction` input
event with the next frame, so input recordings capture it and replays repeat
it. The tree is rebuilt only when the interface changed (otherwise a
comparison of the frame's nodes, about 2 µs), and sent only while an assistive
technology listens.

`PEN_A11Y_DUMP=FILE` writes the tree as text whenever it changes, in a window
or headless (the frame, then each node's role, `#id`, words, states, bounds and
actions), and the `ui=NODE,ACTION[,VALUE]` script step acts on a node as
assistive technology does: NODE is its id, decimal or `0x` hex, and ACTION
`focus`, `blur`, `activate`, `increment`, `decrement`, `set_value`, `expand`
or `collapse`.

```sh
PEN_A11Y_DUMP=a11y.txt pen run --headless --script "key=Tab wait=30 ui=0x20001,activate wait=30 key=F10 key=Tab key=Enter wait=10 quit"
```

[docs/accessibility.md](docs/accessibility.md) has the rest: a headless
run on a private AT-SPI bus worked by an AT-SPI client (`just atspi`,
`PEN_A11Y_ATSPI`), the tree's snapshots, the engine's preferences (a colour
filter the renderer applies, a text scale and reduced motion the game
honors), the game's string tables in the player's language (plural rules,
right-to-left text, font fallback; `PEN_LOCALE`), and the accessibility
audit (`/audit` in the dev tools, `PEN_A11Y_AUDIT`).

## Shipping

`pen build` makes a shippable folder (default `.pen/package`; `just package`
writes `dist/package`): the runtime, named after the game (`gdev` or
`gdev.exe`), Steam's library beside it when the runtime has Steam
(`libsteam_api.so`, `steam_api64.dll`), and `game/`, the bundle in the diagram
at the top.

It ships the **player runtime**: pen built without its default `compiler`
and `devtools` features (`--no-default-features --features steam`), so without
Cranelift or the dev tools. It only loads the `game.cwasm` its package was
precompiled with, and refuses every command that compiles a checkout.
`pen build` ships the runtime in `player/` beside itself. If it is missing,
it asks for `just install-player`; `--runtime EXE` explicitly ships another.
`just install` installs both runtimes. `game.cwasm` is compiled for the
runtime's platform (read from its executable header, or `--target TRIPLE`)
and for a CPU baseline (`--cpu PRESET`, default `x86-64-v2`), not the
packaging machine's CPU.

`pen build` ships only the assets the catalog reaches: what it names, and the
shaders and textures its materials name. Mesh JSON ships in the renderer's
binary form, with lossless byte shuffling and zlib compression when smaller.
Both native and browser hosts restore the original mesh values at load time.
It refuses a runtime built from another pen (different wasmtime or
blot-host): rebuild it with `just install-player`. `pen build --game DIR`
packages a bundle compiled already (`pen export`'s) without the checkout,
for another platform's runtime; for a macOS runtime it makes an app bundle
(docs/shipping.md). The runtime refuses a
`game.cwasm` its package says was made for another runtime.

Each package lists its files with their SHA-256 in `game/files.json`, whose
digest is its version, and `pen build` keeps every version in a
content-addressed store (`.pen/store`, or `--store DIR`). `pen patch OLD NEW
--out FILE` makes a patch between two versions (folders or stored
versions): unchanged files cost nothing, moved ones a copy, changed ones a
binary delta. `pen apply FILE [DIR]`, in the player runtime too, checks the
package is the patch's old version, builds the new one beside it, checks
every file and swaps it in. For gdev, a new program and a changed mesh and
material came to a 46 KB patch for a 120 MB package (docs/assets.md).

| | |
|---|---|
| `just player` | The Linux player runtime, built with cargo-zigbuild against glibc 2.28, which every Steam Linux Runtime container and SteamOS have; `just glibc` checks the result |
| `just windows` | The Windows player runtime, cross-compiled as `x86_64-pc-windows-gnu` with zig: no Windows SDK or MSVC |
| `just install-player` | Installs `just player`'s runtime in `~/.local/lib/pen-runtime/player/`, where `pen build` looks for it |
| `just ship` | Both player runtimes, and the checkout's game packaged with each in `dist/linux` and `dist/windows` |

Both use the `dist` profile (fat LTO, one codegen unit, `panic = "abort"`) and
ship a stripped copy from `target/<target>/dist/player/`. The unstripped build
beside it in `target/<target>/dist/` resolves crash reports, so keep one per
release. [docs/shipping.md](docs/shipping.md) has the details: the CPU
baseline, the build profiles, glibc and the Steam Linux Runtime, the Windows
build, what macOS would take, crash reports, Steam and Steam Auto-Cloud.

### Pushing to another machine

`pen serve` (on a Steam Deck, say) receives packages and `pen push ADDRESS`
sends one (`--package`, default `.pen/package`): only the files the server
lacks, by SHA-256, staged beside its copy and put in place with a rename.
The server listens on 127.0.0.1:7811 unless `--listen 0.0.0.0:7811` says
otherwise, takes pushes with its `--token` only (it makes one up and says it
when given none; `PEN_PUSH_TOKEN` gives it to both ends), keeps packages in
`--dir` (default the data directory's `pushed/`), and starts what a push's
`--run FILE` names only with `--allow-run`, stopping what it started before.
Both are in pen, not the player runtime; it has run between two processes on
one machine, not on a Deck.

### Steam

`just install`, `just player` and `just windows` build with Steam, and
`pen build` then ships Steam's library beside the runtime. Steam starts when
a packaged game is played in a window, or with `PEN_STEAM=1`, and the game
plays on without it when there is no Steam client. The Steam overlay hooks
the swapchain the renderer presents, so it needs no code. While developing,
put `steam_appid.txt` containing `480` beside the executable to test against
Spacewar, and `PEN_STEAM_DEBUG` runs achievement and stat steps
(docs/shipping.md, "Steam"); `PEN_STEAM_APP_ID` makes a store build relaunch
through Steam when started outside it. The game unlocks its achievements
(`FIRST_BRICK`, `FIRST_BUILDING`), raises its stat (`MOST_SALT`) and sets rich
presence (`status`) through its services; without Steam they are answered
`unavailable`. None of this has run against a live Steam client ("Limits").

### Crash reports

A panic on any thread writes a report to `crashes/` in the data directory and
prints its path: what panicked where, the backtrace, the build, the system,
the GPU and the last 30 frame times, at most three reports a run. An error that stops the player runtime writes a
report too, and on Windows shows a message box. `crashes/` keeps the latest 20
reports.
`PEN_CRASH_TEST=N` panics at frame N, to try it on a platform, and
`PEN_BUILD` set while building (a commit, say) goes into the version line.
Shipped runtimes are stripped, so a backtrace has addresses; `addr2line`
against the unstripped build turns them into functions and lines
(docs/shipping.md, "Crash reports").

[docs/texture-compression.md](docs/texture-compression.md) looks at shrinking
them.

## Performance

Measured on the development machine: AMD Ryzen 7 3800X (Zen 2, 16 threads),
NVIDIA RTX 2070 Super, CachyOS (Linux, Wayland, Vulkan).

**Guest time.** The same 600 frames (gdev's default scene, 1280x720, one
60 Hz step each, into play at frame 60), median and p95 after 120 warm-up
frames, with `pen bench --game dist/gdev` and the retired V8 benchmark on the same
`game.wasm`. Three runs each on 2026-10-11, load average about 1:

| Engine | Median | p95 |
|---|---|---|
| V8 (Deno, JSPI) | 0.57–0.60 ms | 0.61–0.64 ms |
| wasmtime, Cranelift without inlining (as `pen dev` compiles) | 0.36–0.38 ms | 0.37–0.39 ms |
| wasmtime, Cranelift with inlining (every other command) | 0.32 ms | 0.34–0.35 ms |

**A frame.** Medians over 600 frames with `PEN_PROFILE_FRAMES=600`, gdev in
play, from docs/determinism.md ("Overlapped frames", 2026-10-11): in a window at
1440x960 with `PEN_PRESENT_MODE=immediate`, a frame takes about 4.5 ms, of
which about 0.7 ms is the guest and 3.6 to 3.7 ms rendering and presenting; at
640x427, about 2.6 ms; headless at 1440x960, about 3 ms.

**Overlapped frames.** `--overlap` computes the next frame in the guest while
this one draws and presents. It hides the guest's time entirely, but rendering
and presenting grow by about as much while the guest runs alongside them, so
the frame interval does not improve today, and headless it gets worse. It
stays opt-in for that reason and because it adds a frame of input latency; it
may pay off when the guest takes several milliseconds (docs/determinism.md,
"Overlapped frames").

**Hot reload.** The development engine compiles gdev's first build in about
105 ms and a reload in about 50 ms (blot-host's `dev_engine`; the date was
not recorded). The runtime's side of a reload, from a new `game.wasm` to the
new build running, takes about 90 ms; the Blot compiler's build before it,
1 to 2 s (gdev's README).

**Loading.** Loading compiles only the pipelines a shader's loaded materials
need, each on its own loader job, and on Vulkan pen keeps compiled GPU
pipelines per adapter in `~/.cache/pen/pipelines` (one file per adapter,
about 2 MB for gdev). gdev settles in 1.3–1.7 s cold and about 0.7 s warm or
with that cache, against 3.6–5.0 s cold before (2026-10-16). Packaged meshes
are binary: gdev's 73 parse in 8.5 ms, against 179 ms as JSON
([docs/render-performance.md](docs/render-performance.md)). A package knows
what its scene draws first (`scenes.json`, written by `pen build`) and reads
and decodes it while the program loads and the GPU opens: gdev's first whole
frame came at 408 ms from the process's start against 489 ms, and the work
after the GPU was ready fell from 138 to 50 ms (docs/assets.md,
"Measured"; `PEN_STARTUP=1` prints the phases).
`just render-packets` renders `dist/packets` headlessly and times loading and
each frame. pen-render logs through the `log` crate: `PEN_FRAME_TIMES` adds its
pipeline compile times, and `RUST_LOG=pen_render=debug` shows them alone.

The player runtime's build profiles cost no measurable frame time
(docs/shipping.md, "Build profiles", measured 2026-10-11 on a machine loaded
by other builds).

## Limits

The runtime is developed and tested on one machine: Linux (Wayland), Vulkan,
NVIDIA. These have not run, or have known gaps:

- **Windows** has never run. `just windows` builds and `pen build --runtime
  …/pen.exe` packages, but there is no Windows machine or wine here;
  docs/shipping.md lists what to check on a first run. CI's `windows` and
  `windows-smoke` jobs are the route to one ([docs/ci.md](docs/ci.md)), and
  have not run yet either.
- **macOS** has not run: there is no Mac here. `pen build` makes an app
  bundle for a macOS runtime, pen and the player pass Clippy for both Apple
  targets, and CI's `macos` job builds, signs and plays it on a runner
  (docs/shipping.md, "macOS").
- **Steam** has never run against a live Steam client; only the way without
  one has. Achievements, stats, rich presence, the Steam overlay and
  Auto-Cloud are untested; `just steam-smoke APP_ID` checks them with the
  game's own app ID once there is one (docs/shipping.md, "Steam"). Steam
  Input is untested too (docs/input.md).
- **The Steam Deck**: the player runtime needs only glibc 2.28 and plays
  in the soldier and sniper containers (`just slr`), but it has not run on a
  Deck. pen sends gamepads, touches and actions (docs/input.md), but gdev has
  no gamepad controls yet, so on the Deck Steam Input's keyboard and mouse
  template is what makes it playable.
- **lavapipe** (`--software`, as CI draws) ran here from Mesa's package
  unpacked into a scratch directory (`VK_DRIVER_FILES` naming its ICD): it
  draws the golden scenes within 1.2% RMSE of the GPU's (its golden
  threshold is 1.5% where the GPU's is 1%), but compiles each
  pipeline on the CPU in seconds, so pen waits up to ten minutes for a
  headless run to settle on a software adapter.
- **Function names in traps and profiles**: both hosts name a trap's frames,
  and the dev tools' profile its functions, from the module's name section
  (and its exports), and place a trap's frames in its source from an
  embedded source map ([docs/source-maps.md](docs/source-maps.md)), but Blot
  emits neither yet: names wait on a pending blot2 patch and source maps on
  blot2 adopting that format, so a Blot game's frames show its exports' names
  and function indices.
- **A recording is tied to its build**: it replays exactly only on the build
  that made it.
- **No texture compression** yet; docs/texture-compression.md is the
  investigation.
- **The data directory is named `gdev`**; a store build should use the game's
  own name (docs/shipping.md, "Steam Auto-Cloud").
